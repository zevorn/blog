## Introduction

As part of the RISC-V International ratification process, version 1.0 is considered frozen for public review. Version 1.0 is considered stable enough to begin toolchain, functional simulator, and implementation development, including in upstream software projects, and no incompatible changes are expected unless serious issues are discovered during ratification. Once approved, the specification will become version 2.0.

The specification includes the complete set of currently frozen vector instructions. Other descriptions considered during development but not appearing in this document are not included in the review and ratification process, and may be fully revised or abandoned. The Standard Vector Extensions section lists the standard vector extensions and which instructions and element widths each extension supports.

## Implementation-defined constant parameters

Each hart that supports the vector extension defines two parameters:

● The maximum bit size of any vector element that can be produced or consumed by an operation, ELEN ≥ 8, which must be a power of 2.

● The number of bits in a single vector register, VLEN ≥ ELEN, which must be a power of 2 and no greater than 2^16.

The Standard Vector Extensions section and architectural profiles may impose additional restrictions on ELEN and VLEN:

● Future extensions may allow ELEN > VLEN by using bits from multiple vector registers to hold one element, but the current proposal does not include this option.

● The upper bound on VLEN allows software to know that indices will become 16 bits wide (the maximum VLMAX of 65,536 occurs when LMUL=8, SEW=8, and VLEN=65,536). Any future extension with more than 64 Kibit per vector register will require new configuration instructions, so software using the old configuration instructions will not see a larger vector length.

The vector extension supports writing binaries that, under certain constraints, execute portably on harts with different VLEN values, provided the harts support the required element types and instructions.

> Code can be written to expose differences in implementation parameters. In general, thread contexts with active vector state cannot be migrated while executing between harts that differ in VLEN or ELEN.

## Vector extension programming model

The vector extension adds 32 vector registers and 7 unprivileged CSRs (vstart, vxsat, vxrm, vcsr, vtype, vl, vlenb) to the base scalar RISC-V ISA.
> Four CSR numbers, 0x00B-0x00E, are temporarily reserved for future vector CSRs, some of which may mirror into vcsr.

### Vector Registers

The vector extension adds 32 architectural vector registers, v0-v31, to the base scalar RISC-V ISA. Each vector register has a fixed VLEN-bit state.

### Vector context state in mstatus

The vector context state field VS is added to mstatus[10:9] and hidden in sstatus[10:9]. Its definition is analogous to the floating-point context state field FS.

When mstatus.VS is set to Off, attempting to execute any vector instruction or access a vector CSR raises an illegal instruction exception. When mstatus.VS is set to Initial or Clean, executing any instruction that changes vector state, including vector CSRs, changes mstatus.VS to Dirty. An implementation may also change mstatus.VS from Initial or Clean to Dirty at any time, even if the vector state has not changed.

> Setting mstatus.VS precisely is an optimization. Software typically uses VS to reduce context-switch overhead.

If mstatus.VS is Dirty, then mstatus.SD is 1; otherwise, mstatus.SD is set according to the existing specification. An implementation may have a writable misa.V field. As with floating-point units, the mstatus.VS field may exist even when misa.V is explicit.

> Allowing mstatus.VS to exist when misa.V is cleared enables vector emulation and simplifies mstatus.VS handling in systems with writable misa.V.

### Vector context state in vsstatus

When the hypervisor extension is present, the vector context state field VS is added to vsstatus[10:9]. Its definition is analogous to the floating-point context state field FS.

When V=1, both vsstatus.VS and mstatus.VS are valid: attempting to execute any vector instruction, or access a vector CSR, raises an illegal instruction exception when either field is set to Off.

When V=1 and neither vsstatus.VS nor mstatus.VS is set to Off, executing any instruction that changes vector state, including vector CSRs, changes both mstatus.VS and vsstatus.VS to Dirty. An implementation may also change mstatus.VS or vsstatus.VS from Initial or Clean to Dirty at any time, even if the vector state has not changed.

If vsstatus.VS is Dirty, then vsstatus.SD is 1; otherwise, vsstatus.SD is set according to the existing specification.
If mstatus.VS is Dirty, then mstatus.SD is 1; otherwise, mstatus.SD is set according to the existing specification.
For implementations with a writable misa.V field, the vsstatus.VS field may exist even when misa.V is cleared.
